# Spike S3: PDF extraction and baseline retrieval (R2)

**Answer:** ingest with **`pdftotext -layout -enc UTF-8`** (poppler 4.00), plus a small Symbol-font repair table. It keeps reading order, keeps a fraction's numerator, bar and denominator on separate lines in the right place, and is about 3× faster than `pypdf`. Neither extractor reproduces formulas reliably, so formulas keep coming from cards only (TP-T2), and section results say `use_for_formulas: false`.

- **Date:** 31 Oct 2026. No model API calls (`TUTOR_LLM=stub`).
- **Inputs:** `jemh104.pdf`, `jemh105.pdf`, `jemh108.pdf` from the dataset's `src/math/`; SHA-256 values match the card anchors. They stay in the git-ignored `data/ncert/`.
- **Retrieval run:** `s3_retrieval-20261031-214425` (`config/app.toml` `c0492e339f06`). **Development numbers only**, on the 15 development card queries. Labels are assistant-proposed, not human.

## 1. Extractors on three Chapter 4 pages

Pages compared: Chapter 4 PDF pages 2, 8 and 10 (printed 39, 45 and 47: standard form, discriminant, summary with the quadratic formula). Chapter 5 PDF page 16 (printed 64) was added for the AP sum formula.

| | `pdftotext -layout` (poppler 4.00) | `pypdf` 6.21.4, default mode | `pypdf` 6.21.4, `extraction_mode="layout"` |
|---|---|---|---|
| Install | External binary (Git Bash has it; Docker needs `poppler-utils`) | Pure Python | Pure Python. Warns that `fontTools` is needed for the CFF Times fonts |
| Time, all 11 pages of Ch. 4 | 0.07 s | 0.24 s | 0.18 s |
| x² | `x2`: the superscript becomes a plain digit | `x2` | `x2` |
| ≠ | Private Use glyph U+F0B9 (a blank box) | Same U+F0B9 | Same U+F0B9 |
| Minus, ±, θ, ∠ in Symbol font | U+F02D, U+F0B1, U+F071, U+F0D0 | Same | Same |
| Simple fractions | Numerator, expression and denominator on 3 lines, in reading order | Numerator and denominator glued into the line, e.g. the AP sum's n/2 comes out as `2n` | Like pdftotext |
| AP sum S = n/2 [2a + (n − 1)d] | `n` / `S = [2a + (n – 1) d ]` / `2` on three lines: recoverable | `S = 2n [2a + (n – 1) d ]`: **wrong**, reads as 2n | Like pdftotext |
| Quadratic formula (fraction with a root) | Radical and bar lost, but tokens in order (`b b2 4ac ,` over `2a`) | Tokens scrambled (`2 4 ,2bb a ca`) | Radical lost; tokens in order |
| Expanded sum with an underbrace (Ch. 5) | Bracket pieces drop out; text kept | Scrambled | Scrambled (`andand andand`) |
| Running head and footer | Head with printed page on line 1; `Reprint 2026-27` footer | Same, with spacing errors in the head (`QUADRA TIC EQUA TIONS`) | Same |

**Findings**
1. Both extractors return the Symbol-font glyphs as Private Use code points U+F0xx, the font code plus 0xF000. `tutor.retrieval.textnorm.repair_symbols` maps the codes found in the three chapters back (≠, ±, −, θ, ∠, Δ, ×, °, …), and blanks the bracket and brace pieces.
2. Superscripts are lost by both: `x2` means x². The maths tokenizer maps `x²` and "x-squared" in queries to `x^2`. PDF text still reads `x 2`, so BM25 matches on `x` and `2` separately.
3. Fractions are the real difference. `pypdf`'s default mode silently turns n/2 into `2n`, which is a wrong formula and not just missing layout. `pdftotext -layout` keeps the parts in place, and `pypdf`'s layout mode is close behind.
4. No extractor gives a safe formula. TP-T2 stands: formulas are cited from cards.

**Recommendation:** use `pdftotext -layout -enc UTF-8` for ingestion. Keep `pypdf` in layout mode as the fallback if poppler cannot be installed somewhere. It is close on these pages, but it needs `fontTools` and was slower. Docling and PyMuPDF (named in the roadmap) were not tried. PyMuPDF is AGPL, and Docling pulls in large models. Neither seems worth it while formulas come from cards anyway.

## 2. Ingestion

`python -m tutor.retrieval.ingest` reads only `jemh104`, `jemh105` and `jemh108`. It refuses `jemh1an` (the answers appendix, D-4) and any other file **before** reading or writing anything.

- **Output:** 78 chunks in `data/ncert/index/chunks.jsonl` (git-ignored): Ch. 4: 18, Ch. 5: 34, Ch. 8: 26. Sections 4.1–4.5, 5.1–5.5 and 8.1–8.5.
- **Chunking:**
  - Split on section headings, which must appear in order.
  - Inside a section, a new chunk starts at each "Example n" (kept with its solution) and at each EXERCISE.
  - Chunks are capped at about 350 words, splitting only after a sentence-ending paragraph.
  - A fraction numerator printed above an "Example" line moves with that example.
- **IDs:** `ncert:jemh104:s4.3:c02`.
- **Metadata on each chunk:**
  - chapter, section number and title, kind (theory, example or exercise);
  - first PDF page and first printed page, plus the full lists of both;
  - source ID, URL and SHA-256;
  - in `manifest.json`: extractor version and arguments.
- **Known gaps:**
  - One chunk, the AP sum derivation (5.4 c01, 639 words), is over the cap because no sentence end falls at a safe break.
  - Exercises are one capped block, not one chunk per question.
  - Exemplar problems are not ingested.

## 3. Hybrid retrieval

The ranked lists, fused with RRF (k = 60, depth 20):
- BM25 over the 25 dataset cards;
- BM25 over the 78 section chunks;
- dense vectors over both, from fastembed `BAAI/bge-small-en-v1.5` (384 dimensions, ONNX on CPU).

The model (65 MB) is downloaded once by `ingest` into `data/models/` (git-ignored). At query time it loads with `local_files_only`, so there are no network calls. Building the index with vectors takes about 6 s; a query takes milliseconds.

## 4. Baseline: development card queries

The 15 development queries, from `plan_freeze(build, 0)["dev_files"]`. Relevant = judged grade ≥ 1 (cards only). MRR is cut at rank 20. group@5 = an acceptable support group is complete in the top 5.

| Arm | Recall@5 | MRR | group@5 |
|---|---|---|---|
| Cards-only BM25, POC tokenizer (the current `textbook-kb` algorithm on 25 cards) | 0.839 | 0.802 | 0.933 |
| Cards-only BM25, maths tokenizer | 0.861 | 0.736 | 0.933 |
| Cards BM25 + dense, RRF | **0.878** | 0.839 | 0.933 |
| Hybrid BM25 (cards + sections), strict | 0.772 | 0.687 | 0.867 |
| Hybrid BM25 (cards + sections), card view | 0.861 | 0.736 | 0.933 |
| Hybrid BM25 + dense, strict | 0.706 | 0.784 | 0.800 |
| Hybrid BM25 + dense, card view | 0.861 | **0.907** | 0.933 |

"Strict" scores the list as served: section chunks take top-5 places and count as misses, because this set labels cards only. "Card view" is the same fused order with sections removed, which is what the card scorer can score.

**How to read it**
- 15 queries and 25 short cards. One query moves Recall@5 by about 0.02–0.07, so none of these differences are significant. These are development numbers, and nothing was tuned on them.
- Dense vectors mainly help ranking: card-view MRR rises from 0.74 to 0.91 when vectors join BM25.
- The strict drop is expected, not a failure. Sections are relevant evidence that this set cannot credit. Section-level labels (Set B, 45 queries, due 2–3 Nov) are what will measure the section side.
- The POC tokenizer has the higher MRR of the two BM25-only arms. The maths tokenizer has better recall. Recheck on Set B before choosing.
