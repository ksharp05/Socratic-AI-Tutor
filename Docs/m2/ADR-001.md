# ADR-001: preserve the team API as the integration boundary

Status: proposed implementation choice, 3 November 2026. Baseline: `b3f0d6d4ee958e4498c16a0aaeca84b141ffdfe0` plus explicitly recorded uncommitted changes. Scope is the local supervised M2 demo.

## Decision
Use the existing team FastAPI application as the candidate single server boundary, retaining its authenticated teacher and student APIs, and keep the existing beta as an explicit mount. Integrate only through narrow, tested service contracts; do not silently merge the separate learner-state stores or assume the mount satisfies teacher authority.

## Alternatives considered
- **Replace the team app with the anonymous beta:** stronger existing text UI and wider source corpus, but misses native graph/teacher authority and would require rebuilding or duplicating those flows.
- **Ignore the beta and use only the original POC:** contains the graph, tools and teacher approval, but currently defaults to templated item hints and a smaller content path.
- **Rewrite both:** highest schedule and regression risk; rejected for the first M2 iteration.

## Consequences and controls
The current mount is not yet an integrated learning journey. A subsequent bridge needs explicit identity/state, scope, trace and authorization contracts; tests must cover stale approvals, learner isolation and answer protection. Keep existing operational APIs and offline fallback available. Human review and final evaluation separation are not replaced by code. No production or public deployment is implied.

## Rollback and validation
The mount is opt-in through `TUTOR_BETA_CONFIG`; disable it to return to the team API. Do not alter the existing beta data. Validate with original API and beta suites, then a same-server student/teacher walkthrough and the separately recorded live/Compose gates. This ADR becomes accepted only after those contracts and evidence exist.
