# Learner deletion and interruption recovery

The handbook requires an explanation of retained/deleted learner data and a two-learner deletion check. The graph previously had no deletion operation. This addition implements a teacher-only logical deletion path and documents actual storage in the [memory policy](../MEMORY_POLICY.md). It does not operate on the original textbooks, frozen builds, completed reviews or final evaluation data.

## Teacher workflow

In the Streamlit teacher interface, open **Data requests**, enter the pseudonymous learner ID twice, confirm authority for the request, and choose **Delete connected learning record**. The screen shows a receipt only after successful cleanup. If deletion returns a pending/busy response, use the same ID to retry. A student credential receives 403; a missing credential receives 401. Deletion is intentionally absent from all agent/MCP tools. The underlying API is `DELETE /learners/{id}` with an authenticated teacher token. Use a synthetic demo learner when demonstrating this destructive operation.

The receipt reports the request ID, learner ID, completion time, number of checkpoint threads and per-table removed-row counts. It explicitly says `logical_deletion_only: true`, `backups_removed: false` and `separate_beta_profile_removed: false`. A repeat completed request returns the same receipt. An unknown ID returns 404 without creating a marker. The application retains a minimal deletion marker/receipt so a still-configured student credential or startup seed cannot restore the learner. Changing token configuration or deliberately reenrolling an ID requires a separate operator procedure; no undo is implemented.

## Persistence and recovery

A deletion marker is committed before scanning or deleting checkpoints. Student overview/history, active-session, turn, leave and resume endpoints then return 410 for that identity, even if a cleanup stage fails. The teacher learner list excludes pending and completed deletions. A complete target work list is committed before deleting any checkpoint, so a retry can still identify its trace rows after an earlier process removed the checkpoint.

Tutor instances register their local checkpoint path with their graph database. New turns register their session ownership before invoking the graph. Deletion inspects all historical snapshots in the current and registered existing checkpoint files; this recovers older conversations lacking the session index. It removes complete owned threads and their pending writes using the installed checkpointer API, then transactionally removes the learner domain rows, traces and reservations and completes the receipt. If domain cleanup fails, those domain changes roll back while the marker/work list remain pending. These separate SQLite stores do not provide one cross-database atomic transaction; durable denial plus retry supplies recovery.

The shared local publication lock orders cooperating turns, history reads, learner overviews and deletion. Cleanup waits for an active turn to finish, then removes that turn's writes. Another instance using the same graph database observes the marker before a subsequent turn. Session IDs cannot move between learner owners, and `api`, `teacher` and approval-thread names are reserved to avoid trace-namespace collisions. A legacy thread with conflicting owners or a shared reserved namespace returns a conflict and leaves the target quarantined for operator review rather than erasing another learner's data.

Graph removal covers mastery, misconceptions, explanation outcomes, quadratic and topic plans, learner events, alerts, stuck state, quiz-application ledger, session reservations/index, learner row, target checkpoint histories/pending writes and target/session-linked trace rows, including common API read traces with exact learner arguments. Shared proposals, publications, source references and answer-key caches remain. The separate anonymous beta profile remains; its existing browser-clear workflow is separate.

## Verification and limits

The initial **16** offline tests passed. The expanded **20** focused tests pass, covering authorization, two-learner isolation, preserved teaching/approval state, historical and multiple checkpoint stores, orphan pending writes with a registered owner, restart/retry after checkpoint failure, rollback after domain failure, stale-context and seeding protection, mixed-owner quarantine, reserved IDs, real in-flight turn ordering, a separate-process file-lock check, teacher widgets/receipt and invalid trace JSON. All records and approvals in these checks are synthetic development fixtures; no actual learner was deleted and no teacher review is implied.

Deletion is limited to the graph database and its registered accessible local checkpoint stores at request time. Unregistered old files, ownerless legacy writes, backups, exports, server logs, browser-held messages, external provider copies and separate beta data are not erased. SQLite row removal does not prove byte-level erasure. Pending requests with inaccessible/corrupt stores require operator recovery. Multi-host/network-filesystem locking and a production deployment remain unverified. [Current acceptance status](STATUS.md).

The final canonical and shared-checkout selections each passed **407 offline tests** across all four suites (103.68 and 103.89 seconds respectively), with both processes exiting successfully. Logs are retained as `Directions/git_delivery/m2_deletion_full_01.log` and `m2_deletion_full_team_01.log`. The [synthetic API example](MEMORY_POLICY_EXAMPLE.json) was captured in a separate isolated local database: student deletion returned 403, teacher deletion completed, subsequent history returned 410, and the second learner view was unchanged. No existing learner data or source corpus was modified.
